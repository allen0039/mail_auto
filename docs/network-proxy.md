# 网络与代理（0.6.0）

全局默认直连。每个邮箱、Telegram 和内置 Agent 可选择「跟随全局」「直连」或一个已保存的代理。局部设置优先，继承只发生一层；代理连接失败不会自动改走直连。后台业务连接忽略 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 与 `NO_PROXY`，以页面设置为准。

## 保存与使用

1. 打开「网络与代理」，填写代理名称、协议、主机、端口及可选账号密码。
2. 点击「加入待保存配置」，再点击「保存代理与连接策略」。表单加入列表后尚未保存到服务器。
3. 在页面设置全局、TG 或 Agent 的连接方式；也可在 TG 通知、Agent 页面单独保存连接方式。
4. 编辑邮箱的「邮箱连接方式」设置单账号覆盖。省略 API 的 `proxy` 字段保留旧设置，新邮箱省略则跟随全局。
5. 保存后运行连接诊断。对比诊断只改变该次探测的出口，不修改已保存策略。

代理只填写主机或 IP，不带协议、路径或账号。IPv6 主机填写裸地址（例如 `fd00::2`），端口独立填写。密码用主密钥加密；编辑时留空保留，删除密码时同时清空用户名。最多保存 20 个代理。代理仍被邮箱引用时不能移除；全局、TG 或 Agent 仍引用的代理也必须先更换策略。

## 协议与 DNS

| 协议 | 连接方式 | 注意事项 |
| --- | --- | --- |
| HTTP | 连接代理后用 CONNECT 建立目标 TCP 隧道 | 代理必须允许目标端口，例如 IMAP 993 或自定义 TLS 端口 |
| HTTPS | 先校验代理 TLS，再执行 CONNECT | 使用受信任证书，代理主机须与证书匹配 |
| SOCKS5 | TCP CONNECT，支持用户名/密码 | 目标域名默认由代理解析；输入 `socks5h` 也按同一方式处理 |

邮箱和 TG 的域名直接交给代理解析，目标 TLS 仍验证原始邮箱或 Telegram 域名。代理自身的主机名需要容器能解析；如果这一步有 DNS 问题，可以填写代理 IP。

Agent 默认在本地验证模型域名的全部解析结果均为公网 IP，然后把已校验 IP 交给代理，TLS SNI 与证书校验仍使用模型域名。这样保留目标 IP 限制，代理入口本身允许是管理员明确保存的 NAS 私网地址。此模式需要本地能解析模型域名。

若模型域名的本地 DNS 不可用，可以在代理配置中勾选「信任此代理在 Agent 连接时解析模型域名并限制为公网目标」。此时本地仍拒绝私网 IP 字面量与 localhost，仍验证目标 HTTPS 证书且不跟随重定向；实际域名解析和最终目标 IP 的安全限制转移到代理，代理端必须拒绝私网、回环、链路本地及云元数据目标。只对自己控制或信任的代理开启，不能声称本地仍能验证代理实际连接的 IP。

## NAS 推荐配置

通常设置全局直连、国内邮箱跟随全局、TG 指定代理；连通性不佳的邮箱再单独指定代理。Agent 根据模型接口实际网络情况选择。

- 代理在路由器或其他局域网设备：填写其局域网 IP 和代理端口。
- 代理与应用在同一用户定义 Docker 网络：填写代理的服务名和容器监听端口，无须额外暴露代理端口到公网。
- 代理在 NAS 宿主机进程：填写容器可达的宿主机地址；代理必须监听容器可达接口，仅允许可信网段和必要认证。
- 普通 bridge 容器内的 `127.0.0.1` 指向容器自身。Linux Docker 可按需在 override 中添加宿主机映射：

```yaml
services:
  app:
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

然后在页面填写 `host.docker.internal` 和代理实际监听端口。宿主机仅监听 `127.0.0.1` 的代理仍不能通过该映射被 bridge 容器访问，须调整监听和访问控制。

TG 保留现有长轮询，通过代理主动连接 Telegram；只为 TG 交互无需增加 NAS 公网入站端口。通知、验证机器人、收命令、回复、编辑消息和按钮回调使用同一连接策略。

## 诊断与生效

「网络与代理」支持目标当前配置、明确直连或指定代理，以及直连/所选代理对比：

- 邮箱：TCP/代理隧道、目标 TLS、邮箱登录与文件夹列表；不读取正文、不移动邮件。
- TG：TCP/代理隧道、TLS、`getMe`；需已保存有效 Bot Token，不发送测试消息或消费更新。
- Agent：受目标限制的连接/TLS，以及不含邮件内容的简短聊天请求；需已保存模型及 API Key，可能产生少量费用，不授予工具闭环能力。
- 全局：以 Telegram 为固定目标，只检查 TCP/隧道与 TLS，不需要 Bot Token；不代表全部目标均可达。

失败报告安全阶段/错误码和耗时，HTTP 407 单独报告代理认证失败；CONNECT 被拒绝时显示响应状态码；SOCKS5 失败可能由认证、目标解析、出口或代理端限制造成。诊断不会自动切换出口。必须测试真实目标端口，网页可访问不等于 IMAP 端口可用。

邮箱有效出口变化后，后台监控安全重连，下一次写入复用边界替换旧连接；进行中的写入不因代理设置被强行重放，结果未知仍进入待核验。代理变化不改变邮箱身份、不清空现有索引。TG 代理变化重启长轮询但保留绑定、接收位置及通知配置，不因网络设置丢弃待发通知。

Agent 有效出口（代理地址、协议、认证或 DNS 信任模式）变化时，在同一事务中停用 Agent、清空能力检测、取消未完成轮次并使未完成方案失效。重新运行聊天/工具闭环检测后再启用，独立固定任务保持原配置。

管理网页与入站 MCP 的访问路径由部署反向代理和调用方决定；应用的业务代理不会替外部 MCP 客户端配置出口。本地健康检查和 MCP 入口自检始终直连。

## 管理 API

接口只对完成首次设置的管理员会话开放；写入和诊断需同源与 CSRF。

| 接口 | 说明 |
| --- | --- |
| `GET /api/network` | 返回 `version`、`global`、`telegram`、`agent` 及脱敏 `profiles` |
| `PUT /api/network` | 完整保存网络配置，需当前 `version`；旧版本返回 409 |
| `POST /api/network/check` | `{scope, account_id?, mode, proxy_id?}`；scope 为 `global/account/telegram/agent`，mode 为 `configured/direct/proxy` |
| `POST /api/accounts` / `PUT /api/accounts/:id` | 可选 `proxy: {mode: "inherit/direct/proxy", proxy_id: ""}`，指定代理时填写 ID |

策略对象为 `{mode, proxy_id}`。全局不能选择 inherit；direct/inherit 的 proxy_id 必须为空。代理 profile 包含 `id`、`name`、`protocol`、`host`、`port`、`username`、`trusted_remote_dns`；写入可附带 `password` 或 `clear_password`，读取只返回 `password_set`。新代理可省略 ID 由服务端生成，页面使用随机 ID 保留待保存策略引用。

schema 11→12 只新增网络相关表。升级、备份和回退见 [运维文档](operations.md)。
