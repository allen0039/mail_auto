# Mail Auto 0.5.0 功能与优化方案

日期：2026-11-05。基线：当前工作区的 0.4.0 代码与文档。

这份方案针对已经具备规则、任务、MCP、原邮箱文件夹整理和 Telegram 通知的版本，目标是先把长期运行的稳定性、同步成本和运维闭环做扎实，再增加报告、原生标签和客户端规则导入等能力。

当前工作区已先落地 P1-B 的任务规则绑定切片：任务可跟随全部启用规则，或保存指定规则 ID 与版本；运行、预览和 AI 批次统一校验绑定快照及高优先级覆盖。其余逐封结果、导出和继续处理入口仍按后续阶段实施。

## 一、当前判断

现有版本已经能完成“同步 → 预览 → 受控整理 → 核验 → 记录 → 通知”的闭环，服务端也没有把模型调用、任意正文指令或无限制管理员权限放进自动任务。`go test ./...` 当前全部通过。

仍有四类事情会直接影响使用体验：

1. 0.4.0 的工作区变更尚未形成正式发布物，真实 QQ/网易/iCloud 写入和真实 Codex/ChatGPT 周期任务仍没有专用验收证据。
2. 自动同步每轮通过 `UID SEARCH` 和 `UID FETCH` 校对 UID 与标记，尚未使用 CONDSTORE/QRESYNC；邮箱规模变大后会重复读取大量不变数据。
3. 本地搜索主要依靠 `lower()`/`instr()` 和 `count(*)`，主题/发件人搜索及逐条标签读取会随着索引增长变慢。
4. 任务运行有总计数和状态，但任务目前使用账号全部启用规则，缺少明确规则绑定、逐封决定历史、可导出的结果报告；密钥轮换和外部监控也需要补齐。

## 二、推荐优先级

| 优先级 | 目标 | 主要交付 |
| --- | --- | --- |
| P0 | 发布收口和真实兼容性 | 0.4.0 正式镜像/版本、schema 7 迁移与恢复演练、三类邮箱只读/受控写入矩阵、真实 MCP 客户端联调 |
| P1 | 同步与搜索性能 | CONDSTORE/QRESYNC 能力协商和回退、文件夹同步游标、搜索索引/分页优化、批量读取标签、并发与限流调整 |
| P1 | 任务可解释性和可控性 | 任务绑定规则版本、运行差异预览、逐封结果、继续处理入口、结果导出和更清晰的失败恢复 |
| P1 | 安全与运维 | 在线密钥轮换、定时备份校验、`readyz`/指标、队列积压和同步延迟告警、审计筛选导出 |
| P2 | 增值能力 | 报告/摘要、原生 IMAP 标签能力探测与可选写入、客户端规则安全导入 |
| P3 | 大范围产品化 | SMTP/自动回复、多用户、服务端模型 API、完整 Webmail；另立需求评审，不放进 0.5.x |

推荐先做 P0 + P1。这样能先证明“真实邮箱长期运行不会漏信、重复移动或无法恢复”，再扩展用户可见功能。

## 三、阶段计划

### P0：0.4.0 发布收口（建议先做）

- 将当前未提交的 0.4.0 代码和文档冻结成可回滚的版本，发布 amd64/arm64 镜像并记录 digest；同步修正 README、CHANGELOG、Compose 和验收记录中的版本/镜像状态。
- 在隔离账号上分别验证网易 163/126/yeah.net、QQ、iCloud：TLS 登录、目录发现、全历史元数据同步、IDLE/轮询、UIDVALIDITY 变化、断线重连、移动到专用测试目录、写后核验和未知结果恢复。
- 使用真实 MCP 客户端验证 OAuth 授权、刷新/撤销、长期连接、外部周期调用和任务幂等键。客户端没有真正建立周期任务时，页面和文档继续明确显示“等待外部触发”。
- 做一次 schema 6→7 升级、重启、备份、干净卷恢复和回退演练；恢复后核对管理员、主密钥、邮箱密文、邮件引用、任务和 outbox 状态。

出口：有发布物、回滚物和真实兼容性矩阵；没有真实测试邮件进入生产任务。

### P1-A：同步成本和搜索性能

1. **文件夹同步状态**：增加每个账号/文件夹的同步状态记录，保存 UIDVALIDITY、UIDNEXT、最高 MODSEQ、最后全量校对时间、最近错误和能力探测结果。能力存在时使用 CONDSTORE/QRESYNC 获取变化 UID；不支持时保持当前 `UID SEARCH` 全量回退。
2. **避免错误优化**：能力协商必须按服务器结果缓存并可失效；UIDVALIDITY 变化、MODSEQ 异常或服务器返回不完整时立即回到安全全量扫描，不能把“没有变化”当成事实。
3. **搜索索引**：先用基准数据决定是否启用 SQLite FTS5。主题、发件人、文件夹、日期、已读/星标和大小分别保留结构化过滤；若 FTS5 在目标镜像不稳定，则采用规范化 sender/domain 列和组合索引作为回退。
4. **分页和列表**：默认使用游标分页；总数改为可选或短时缓存，避免每次页面请求都 `count(*)`。标签一次批量读取，禁止按邮件逐条查询。
5. **资源控制**：为每个提供商记录连接、命令耗时、重试、限流和同步滞后；按账号串行、跨账号小规模并行，并在服务器退避时降低校对频率。同步和整理共享账号级租约，避免后台校对覆盖刚完成的移动。

建议的 schema 8 变化为 `folder_sync_state`、搜索辅助索引/FTS 表及能力缓存；迁移要保留现有 `ref`，不能因重建索引改变外部引用。

出口：在 1 万、10 万和 50 万封合成数据上验证 p95 搜索、首屏列表和增量同步时间；全量回退与 QRESYNC 结果逐 UID 对账一致。

### P1-B：任务与规则可解释性

- 新增任务与规则的显式绑定。任务保存 `rule_id + rule_version` 列表，默认可选择“跟随账号全部启用规则”；运行时保存实际规则快照摘要，规则改动后旧运行自动失效。
- 预览页增加“将移动到哪里、为什么跳过、哪些字段未知、这次与上次的差异”；支持 JSON/CSV 脱敏导出，不导出正文和凭据。
- 增加逐封运行项视图：规则命中、保护原因、AI 待判断、计划动作、远端结果、未知结果和核验时间。现有操作表仍是事实来源，任务表只保存汇总。
- 增加“继续处理本任务”入口：沿用安全游标新建一次运行，明确显示还有候选；不能通过重试绕过每日额度、授权过期或未知结果。
- 对同一账号的多个任务增加公平调度和冲突提示；失败、待核验、通知失败分别展示，继续保持通知不会重跑邮件动作。

建议新增 `task_rule_bindings` 和 `task_run_items`（或等价的查询投影），并继续采用版本号/幂等键/邮件签名复核。

出口：规则修改、任务暂停、账号撤权、服务重启和网络应答丢失后，逐封状态都能解释，且不会重复移动或误报“全部完成”。

### P1-C：安全与运维闭环

- **在线密钥轮换**：密文带 key version；轮换期间双 key 读取、单 key 写入，完成后可验证全库重加密并撤销旧 key。数据库和密钥备份必须有匹配清单，失败时保持旧 key 可恢复。
- **备份自动化**：提供宿主机可调用的定时备份脚本/说明、备份 manifest（schema、版本、数据库校验和、key fingerprint），并支持在临时卷自动打开备份做健康检查。
- **可观测性**：新增只读 `readyz` 和受保护指标/诊断接口，至少包括各账号同步滞后、最近错误、任务队列年龄、待核验数量、outbox 积压、Telegram 失败率、数据库大小和 WAL 大小。不要在指标中写入主题、发件人、正文或 token。
- **告警分层**：服务停机不可依靠自身 Telegram；提供外部探针检查 `/healthz`/`/readyz`，服务内只负责任务失败、同步持续失败和 outbox 积压提示。
- **审计**：支持按时间、账号、动作和结果筛选/导出，保留现有 90 天清理策略；导出默认脱敏，不能导出凭据或正文。

出口：密钥轮换、备份恢复、容器重启、磁盘接近上限和通知服务不可用都有可操作的诊断信息。

### P2：用户可感知增值能力

1. **报告/摘要**：先做不调用模型的统计报告：按账号/文件夹/日期统计新增、未读、已整理、待处理和失败；通过 Web、MCP 和 Telegram 摘要查看。需要语义摘要时仍由外部 AI 读取有界数据。
2. **原生标签**：先扩展能力探测，区分 IMAP KEYWORD、SPECIAL-USE、厂商扩展和客户端私有标签；对每个提供商显示 `read/write/verified`。没有可验证的读写闭环时继续使用原邮箱文件夹，不做“看起来成功”的标签写入。
3. **客户端规则导入**：不尝试读取网页邮箱私有规则。支持用户上传或粘贴一个受限、可审阅的规则格式（例如 Sieve 的安全子集），解析成现有规则模型，先预览冲突、循环和未知动作，再保存为暂停规则。

## 四、暂不建议加入

- SMTP 发信、自动回复、转发、退订和永久删除：会把风险从“移动邮件”扩大到外发和不可逆操作。
- 服务端直接调用模型 API：当前外部 MCP 已能完成判断，先把权限、成本和数据边界留在客户端。
- 多用户/团队/共享邮箱：需要重新设计租户隔离、账单、审计和授权，不适合与同步性能改造混做。
- 完整 Webmail、附件下载/OCR、向量库：资源和隐私成本明显增加，先验证元数据整理的长期稳定性。

## 五、统一验收门槛

- `go test ./...`、`go test -race ./...`、`go vet ./...`、漏洞扫描和迁移测试全部通过。
- 三家提供商各有只读和专用测试文件夹写入用例；覆盖 UIDVALIDITY 变化、断线、服务器限流、重复回包和未知写入结果。
- 合成 1 万/10 万/50 万封索引的同步、搜索、任务预览和数据库增长基准达到发布前记录的阈值。
- 任务并发、重复 run_key、规则/授权版本变化、暂停/撤权、进程重启、Telegram 失败和外部客户端迟到提交均有回归用例。
- 桌面与 390px 手机页面无横向溢出；敏感字段在 HTML、日志、审计、指标、MCP 和通知中均不回显。
- 升级、回滚、联合恢复和在线密钥轮换至少各演练一次，保留脱敏报告。

如果按本方案执行，建议版本顺序为：0.5.0 做发布收口、同步/搜索、运维和任务规则绑定；0.5.1 做逐封报告、导出和摘要；0.6 再决定原生标签与规则导入是否值得投入。
