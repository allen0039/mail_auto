# Mail Auto：内置 Agent 与 Telegram 交互管理实施方案

编制日期：2026-11-13，Asia/Shanghai。代码核查基线：`0e960a1`，运行版本 `0.4.20`，数据库 schema 9。

状态：待实施设计。本文供 Claude 实施、Codex 后续独立审计验收使用。本文的编写不代表任何功能已经实现、测试通过或部署完成。

## 1. 目标与实施边界

首版目标：管理员在 Telegram 私聊中，通过自然语言创建和修改固定整理规则、试运行、创建定时任务、启用或暂停任务、按明确指令执行任务、查询进度与接收结果。模型采用可配置的 OpenAI 兼容 API。

首版完成下面这个闭环：

```text
Web 配置模型、授权与 TG 绑定
  → TG 描述需求、补充条件
  → Agent 生成结构化草稿
  → 展示规则与任务差异、试运行和受影响任务
  → 按具体方案确认启用
  → 现有任务系统执行
  → TG 按真实记录反馈进度与结果
```

### 1.1 首版必须完成

- OpenAI 兼容 Chat Completions Provider，可配置 Base URL、API Key、模型，分别检测聊天和工具调用。
- Go 进程内的轻量 Agent，工具参数严格校验，读写采用现有 `mail.Service` 业务路径。
- Telegram 私聊绑定、长轮询、连续对话、结构化操作卡片和回调。
- 固定规则和任务的查询、草稿、修改、预览、启用、暂停、执行、停止剩余项及结果通知。
- 持久化 inbox、对话轮次、工具执行记录、待确认方案、交互 outbox；重启和重复投递不能重复创建规则、任务或任务运行。
- Web 中可查看模型状态、绑定、授权、近期会话和任务关联，并可撤销及停用。
- MCP 与原有 Web 功能回归验证，保留现有部署形态和邮箱操作保护。

### 1.2 后续阶段，不纳入首版完成承诺

- Responses Provider，以及其他原生供应商协议。
- 持续 AI 语义分类、内置 AI 定时 worker、按正文判断是否需要回复。
- Web 完整聊天界面、多管理员、群聊、语音、图片、附件解析。
- 任意 shell、任意 SQL、通用 HTTP 工具、任意第三方 MCP 动态接入。
- 发送邮件、永久删除、自动处理附件、原邮箱文件夹重命名与删除。
- 模型路由、自动切换供应商、复杂多 Agent 框架、向量库或长期语义记忆。

首版对 `engine=ai` 的任务只显示现有配置与状态；禁止 Agent 触发会进入 `awaiting_ai` 的运行。收到持续 AI 分类需求时说明尚未支持，提供固定条件规则的可行替代。不得留下无人消费的 AI 运行。

### 3.1 不能跳过的现有行为

- `CheckAccess` 目前仅识别管理员、MCP token、任务服务身份。构造 `Access{Owner:"agent:..."}` 本身不能成为合法身份；必须实现持久化授权与校验分支。
- `TaskRun`、`TaskRuns`、`CancelTaskRun` 对非管理员有 owner 隔离。TG 若要管理内置日程产生的 `svc:` 运行，需要新增有范围的运行管理能力，不能改成所有 `task_manage` token 都可跨 owner 查询和取消。
- `SaveTask` 新建强制暂停和观察模式。创建、预览、改变模式、启用必须按实际返回版本推进；不能向用户声称一次 upsert 已开始执行。
- `resolveTaskRules` 不接受把任务显式绑定到禁用规则。因此“禁用新规则 + 显式绑定它的新任务”不能直接同时保存到当前业务表。任务先保存在 Agent 方案中，用只读草稿预览评估；确认启用规则后才创建实际任务，不能为预览临时启用规则。
- `authorizedAutomation` 当前要求调用主体可读策略中的全部来源文件夹。Agent 授权覆盖不足时返回明确限制，引导管理员在 Web 调整；不得伪造管理员身份、静默扩权或直接绕过策略。

另有两项回归风险：新增或启用规则会影响“跟随全部启用规则”的现有任务；当前 SQLite 连接池仅一个连接，任何模型或 Telegram 网络请求都必须在事务和已打开游标之外执行。

## 4. 架构与代码组织

```text
Telegram API ←→ telegram transport / durable inbox / reply outbox
                              ↓
                    Agent runtime / proposals
                         ↓             ↓
                  Provider 接口     共享工具注册层
                         ↓             ↓
              OpenAI-compatible     mail.Service
                                       ↓
                       规则 / 日程 / 任务 / IMAP 核验

现有 MCP adapter ───────────────→ 共享工具注册层
现有 Web 管理 ─────────────────→ 同一业务服务和授权
```

建议目录与职责如下，具体文件拆分可按现有风格调整：

| 位置 | 职责 |
| --- | --- |
| `internal/modelprovider/` | Provider 接口、Chat Completions、错误分类与能力检测；不访问邮箱或业务数据库 |
| `internal/agent/` | 对话轮次、上下文预算、模型循环、提案与确认、恢复监督器 |
| `internal/telegram/` | Bot API 客户端、轮询、消息/回调标准化、分片与队列投递 |
| `internal/mailtools/` | 有名称、Schema、风险与处理器的共享业务工具；调用 `mail.Service` |
| `internal/mail/agent_access.go` | Agent grant、动态校验、受控的跨 owner 任务管理业务方法 |
| `internal/store/agent.go`、`telegram.go` | 新增表、索引、迁移和必要事务帮助函数 |
| `internal/admin/agent.go`、`telegram.go` | 管理设置、测试、授权、绑定与记录 API |
| `internal/admin/web/agent.js` | 设置、检测、绑定、授权和操作记录界面 |
| `cmd/mail-auto/main.go` | 注入依赖，按生命周期启动和停止 |

依赖方向：`mailtools → mail`，`mcpserver → mailtools`，`agent → mailtools + modelprovider`。`mail` 不导入 Agent、MCP 或 Telegram 包。Telegram 与 Agent 通过窄接口连接，避免互相导入。

先抽取首版实际需要的工具。现有 AI batch 和原始邮件操作工具可以暂留 MCP adapter；共享层统一后再逐步迁移。不得为一次性迁移全部工具改写所有稳定接口。

## 5. 模型 Provider 契约

### 5.1 设置与协议

- 首版只实现 `api_type=chat_completions`，接口预留扩展，不显示尚不可用的 Responses 选项。
- Base URL 定义为 API 根地址，例如 `https://api.example.com/v1`；由客户端追加 `/chat/completions`。展示最终请求地址，避免 `/v1/v1` 或重复路径。
- 配置含 `version`、`enabled`、`base_url`、`model`、密钥设置/清除、超时和已验证能力；返回 `key_configured`，不回显密钥或密钥片段。
- API Key 使用现有 Vault，AAD 绑定 Provider 实例 ID；空值表示保留，清除需独立字段，规则与现有 Bot Token 设置一致。
- 不强依赖 `/models`。模型名称允许手工填写；缺少模型列表能力不阻止接入。
- 默认 `stream=false`，依靠 TG 接收回执和后台任务状态改善等待体验。SSE 不属于首版验收要求。
- 不默认发送 `temperature`、推理强度等可选供应商参数。输出长度参数按已检测能力选择并写入配置；不支持所需基本能力则明确拒绝启用。
- `strict`、`parallel_tool_calls` 等可选参数按能力检测启用；无论供应商是否遵循 Schema，应用端始终校验。
- 不实现对不支持工具调用模型的文本 JSON 猜测降级。

### 5.2 内部输入输出

Provider 接口至少抽象 `Complete(ctx, request)` 和 `Probe(ctx, settings)`。中立请求携带 messages、tools、输出限制；结果携带 assistant 文本、完整 tool calls、finish reason、可选 usage 和固定错误码。

Chat Completions 适配器必须：

1. 保留 assistant 工具调用消息，并以匹配的 `tool_call_id` 提交每个结果；支持同一响应出现多个调用。
2. 解析真正的 JSON 参数，拒绝未知工具、未知字段、尾随 JSON、越界枚举、过深嵌套及不完整参数。
3. 即便模型返回并行调用，首版按收到顺序串行执行；后续调用重查权限、资源版本和停止状态。
4. 一次响应中有写入提案时先完成依赖分析；前序依赖失败不能继续执行依赖它的后续写入。
5. `finish_reason=length`、截断工具参数、空响应和无效响应均不得触发业务写入；仅完整、验证通过的调用进入工具层。
6. 供应商 usage 缺失时标为未知，不把估算值展示成真实账单；供应商返回原始错误不直接进入日志或 TG。

### 5.3 连接测试

Web 提供两项独立测试，测试只执行本地无副作用的 `echo` 工具：

| 测试 | 成功条件 |
| --- | --- |
| 聊天测试 | 实际请求成功，得到有效非空回复 |
| 工具闭环测试 | 模型返回指定本地工具 → 参数校验 → 本地返回结果 → 模型读取工具结果并完成回复 |

仅聊天通过时显示“可聊天，未验证工具调用”，不得启用写操作 Agent。能力检测结果绑定 Provider 配置版本、模型与地址；修改任一项即失效。

### 5.4 网络、重试与数据边界

- 默认仅允许 HTTPS，无 URL userinfo、fragment 或 query；仅管理员可配置地址，模型和 TG 都不能修改。
- 禁止跟随重定向，避免 Authorization 转发；拒绝元数据地址、回环和私网目的地。若后续需要本地模型，单独实现管理员显式主机白名单，不能首版默认允许所有私网。
- 地址解析和实际连接都校验目标，覆盖 DNS 重绑定与 IPv6。测试用假服务通过注入客户端或 transport，不能关闭生产检查。
- 默认不读取进程代理配置，避免隐式代理绕过目的地址检查；如实际部署需要代理，必须显式配置、记录信任边界并增加测试。
- 建议起始值：单次请求 60 秒、一次对话轮次总计 120 秒、最多 8 次模型请求和 20 次工具调用。全部为单次工作上限，区别于每日邮件额度。
- 建议响应体上限 2 MiB、工具参数 32 KiB、单次工具输出 32 KiB。大结果分页，超限可观测且不静默截断 JSON。
- 网络错误、429、部分 5xx 在轮次总期限内最多重试两次，遵循有界 `Retry-After` 与抖动。401/403、Schema 不兼容、参数错误不循环重试。
- 仅在工具调用响应尚未持久化时可重试生成；一旦 assistant 调用已持久化，恢复必须沿用原调用、action_id 和业务结果继续协议，不能重新生成另一批 ordinal 后当作新操作执行。无法无歧义对应时中断，报告已完成项并要求新的明确指令。
- 首版工具无需读取正文；模型只获得用户对话和本次任务必要的、受授权元数据。邮件主题、发件人、规则文本都按不可信数据处理。

## 6. Agent 身份、授权与共享工具

### 6.1 独立 Agent grant

新增持久化 Agent grant，至少包含：ID、版本、管理员版本、启用/撤销、有效期、账号、每账号文件夹范围、动作集合和绑定主体。`Access.Owner` 使用独立前缀，例如 `agent:`，并在 `CheckAccess` 增加明确分支。

身份必须由服务端根据有效 TG 绑定解析，模型只能提交业务参数。模型提供的 owner、管理员版本、grant ID、run_key 或确认 token 不得成为身份依据。

- 每次工具调用、确认执行、任务入队及实际写入均校验当前授权；不能仅检查轮次开始时的快照。
- Agent grant 与现有自动化策略、账号写入开关取交集。它不能授权业务策略禁止的动作。
- 初始勾选权限为查询；规则管理、任务管理、手动运行、任务运行管理按需授权。执行能力仍受 observe/execute 等现有策略约束。
- grant 过期、撤销、范围收窄、管理员版本改变立即阻止新写入；待确认方案失效。在途远端结果继续走原有安全核验，不重放 MOVE。
- 授权检查也覆盖数据外发：每次模型请求前、接纳模型响应时和 outbox 发送前核对当前 binding/grant/admin/config 版本。grant 改变后保守使旧上下文 epoch 失效、取消旧模型请求并抑制旧版本待发内容；不把已撤权范围的历史工具结果重新发给模型或 TG。只可向仍有效的绑定发送不含邮箱信息的重新授权提示。
- 不把真实 MCP bearer token放进模型消息；Agent 身份不必创建或暴露长期外部 MCP token。

### 6.2 内置任务的查看与停止

为 Agent 增加内部专用的任务运行管理能力，例如 `task_run_manage`。它只通过有效 Agent grant 获得，不加入普通 MCP token 现有可选动作。

新增服务方法或内部 Actor-aware 分支，应同时验证：

- 原任务、该次运行快照和账号均在授权范围内；来源文件夹、目标动作和可见结果不越界。
- 当前管理员版本有效，历史运行不得因当前任务改名或缩小范围而泄露原来范围的邮件信息。
- 只允许查询或请求停止；不允许修改原 run owner、接管租约、执行其冻结计划或伪装成 `svc:`。
- grant 未授予该能力时，继续保持原有 owner 隔离。
- Agent 的管理审计记真实操作者，执行主体仍为原任务 owner。

取消规则任务应复用已有停止语义。首版不跨 owner 取消 AI batch：若无法通过原业务路径安全处理，显示能力限制并引导原入口。不能为了统一取消而放宽 AI batch 的 owner 检查。

### 6.3 工具注册与首版白名单

每个工具定义名称、输入 Schema、结果 Schema、权限、风险类别、幂等属性、最大结果和处理器。MCP annotations 只作提示，授权来自服务层。

| 工具组 | 首版能力 | 写入方式 |
| --- | --- | --- |
| 账号/目录/能力/策略 | 查询已授权账号、原邮箱目录及现有策略 | 只读 |
| 规则 | 列表、详情、保存禁用草稿、预览、修改/启用/暂停提案 | 草稿或提案 |
| 任务 | 列表、详情、保存暂停观察草稿、预览、修改/启用/暂停提案 | 草稿或提案 |
| 运行 | 查询、按明确请求触发固定规则任务、请求停止剩余项 | 服务端授权与幂等执行 |
| 会话 | 查询当前方案、丢弃草稿、停止当前轮次 | 服务端确定性命令 |

模型可请求准备提案，不能直接提供已通过确认的标志。启用/修改生效规则等处理器返回 `confirmation_required` 和服务端创建的提案，不直接调用底层写方法。MCP 继续使用其既有授权方式，不被迫采用 TG 按钮流程。

不向首版 Agent 暴露 `SaveAutomationPolicy`、管理员凭据、API 设置、Bot Token 设置、外部 secret、原始 IMAP、`mail_execute`、任意 `mail_ai_*` 或永久删除能力。

现有 MCP 对 automation token 的原始 search/get/preview 限制保持原样。共享处理器采用显式调用来源与能力配置，不能借提取代码把现有边界消掉。首版 TG 试运行优先走任务预览，统一应用保护和策略。

### 6.4 配置合并与规则绑定

- 模型修改采用受控 patch：先加载现有对象，再合并用户明确要求的字段；不接受缺字段的完整对象覆盖。
- `max_batch`、未读/星标保护、Since、历史范围、稳定延迟等由服务端从现有任务/策略继承并计算有效值，回复中展示实际值。
- 用户明确要求改保护或批次数量时，走显示旧值/新值的提案，仍不得突破 Web 授权。
- “运行这条规则”默认绑定指定规则及不可跳过的高优先级规则闭包，保存返回的实际 rule IDs/versions。
- 只有用户明确选择“跟随全部启用规则”时才使用空 `rule_ids`；回复必须说明未来启用规则也会影响该任务。
- 针对新禁用规则，新增内部只读 `PreviewDraftWorkflow` 或等价服务方法：验证草稿、策略、文件夹和版本，在内存中形成“若启用该草稿”的规则快照，复用任务预览的条件引擎、优先级、保护、分页与计数。待建任务存于 Agent 方案，不写入一个绑定禁用规则的非法 automation_task；预览不修改任何规则 enabled 状态。不得复制出另一套判断引擎，或用空 rule_ids 掩盖绑定失败。
- 现有任务的 rule versions 过期时提示冲突并重新预览，不能静默替换为最新版本后运行。
- 目的文件夹不存在时要求管理员先在现有 Web 创建并授权，首版不自动建文件夹。

## 7. 提案、确认与业务幂等

### 7.1 何时需要确认

| 行为 | 策略 |
| --- | --- |
| 查询、试运行、保存禁用规则或暂停观察任务草稿 | 在明确需求下可直接完成并回复草稿状态 |
| 启用规则、修改生效规则、启用/修改执行任务或日程 | 展示具体差异和影响后确认 |
| “执行任务 X”且其当前已授权、启用、版本未变 | 明确指令可授权一次运行，服务端绑定 task/version 和本次操作 ID，不重复弹确认 |
| 执行暂停任务、首次开启 execute、范围或动作变化 | 先展示具体方案再确认；不能滥用 `manual=true` 绕过暂停 |
| 暂停任务或停止指定运行剩余项 | 明确指令直接执行，不依赖模型或额外确认；已完成动作保留 |
| 扩大账号权限、打开正文读取、启用写入或内部日程授权 | 仅在 Web 管理设置完成 |

“看看”“帮我分析”“创建草稿”不能被解释成执行邮件修改。已经确认的固定任务后续按既有授权调度，不为每轮自动运行再次要求确认。

### 7.2 冻结提案

提案至少绑定：操作者和绑定版本、grant/admin 版本、账号、规则版本/摘要、任务版本、策略版本、文件夹映射/写入配置版本或等价摘要、受影响任务、操作步骤、有效期限和规范化参数摘要。

- 默认 10 分钟过期；配置/规则/策略变化、重新绑定、`/new` 或修改条件使相关提案失效。
- 预览必须标明扫描范围、扫描数、分页、匹配/保护/未知字段数量和每批上限；第一页数量不能说成全邮箱总量。
- 显示启用规则会影响的现有任务，尤其是跟随全部规则的任务；影响集合变化后旧确认不能继续。
- 若影响集合含 Agent 无权管理的任务，拒绝从 TG 启用或修改该规则，引导 Web 管理；不泄露范围外任务的名称或邮件详情，也不静默允许跨范围影响。
- 首版试运行只读本地元数据，是解释和决策依据，不承诺冻结未来定时运行的全部邮件。实际执行继续使用原有新鲜度和保护复核。
- callback_data 仅存短随机 token 和动作，不存整段 JSON、用户 ID 或“已授权”标志。token 建议至少 128 bit 随机数，只存哈希，长度小于 Telegram 64 字节限制。
- 确认处理器重查真实 `from.id`、私聊 chat、bot、消息/提案关联、期限及版本，以 CAS 消费提案。模型无法调用“确认”工具。
- 已有启用规则可先保存实际暂停观察任务再预览。新规则流程按“禁用规则草稿 + 方案中的待建任务 → 只读草稿预览 → 确认 → 启用规则 → 创建实际暂停观察任务 → 按确认调整模式 → 启用任务”推进，各步骤用实际返回版本；最终消息分别说明规则和任务状态。

### 7.3 防重复必须覆盖四层

1. Telegram 事件：`UNIQUE(bot_id, update_id)`；相同 update 不再创建轮次。
2. Agent 工具：每次已解析调用持久化 `turn_id + ordinal` 和规范参数摘要；重复执行返回保存结果。服务端为用户业务意图建立 action_id，并将模型调用与它关联；ordinal/tool_call_id 只用于协议，不可作为生成新业务操作的唯一依据。重生成或循环提出同一已接受动作时复用原 action_id；草稿修改更新同一工作流资源，不重新建同名资源。
3. 业务修改：为规则/任务创建和版本修改提供服务端 `mutation_id`；业务写入、审计和成功结果在同一 SQLite 事务中提交。不能只在外层“先记工具已开始，再 SaveRule，再记成功”。
4. 任务运行：run_key 由服务端从持久化用户操作 ID 生成，重试沿用；不得由模型生成。相同指令重复投递返回同一运行，用户另发一条明确执行指令才是新运行。

业务层可增加内部 `SaveRuleWithMutation`/`SaveTaskWithMutation` 等窄接口，复用原有校验和事务实现；现有调用保持兼容。幂等记录重复时校验同一 key 的参数摘要、目标及操作者，参数改变返回冲突。

不能承诺 Telegram 消息或远端 IMAP 的全局 exactly-once。这里要求的是本地业务创建/入队在约束下幂等，以及远端未知结果不被盲目重放。

### 7.4 多步骤失败与恢复

提案状态建议为 `pending → accepted → applying → applied`，另有 `expired/rejected/invalidated/partial/failed`。单个步骤保存 mutation_id、目标版本和结果。

- 接受状态、操作者、第一步意图持久化后再执行。崩溃后读取已提交的业务幂等结果继续，不重新生成另一套步骤。
- 规则创建成功、任务创建失败时显示部分完成和实际资源 ID；不得假报全成功或重新建另一条规则。
- 下一步发生版本冲突/授权变化时停止并失效，刷新方案；不自动覆盖他人修改。
- 不自动回滚已生效规则/任务，因为可能已影响其他任务；显示差异，由用户明确选择修复方案。
- 对“操作已入队但 TG 结果发送失败”只重试消息，不能再次提交业务操作。

## 8. Agent 对话、上下文与生命周期

### 8.1 轮次状态

建议状态：`queued → running → waiting_confirmation / completed`，以及 `cancelled/failed/interrupted`。任务长期执行通过关联 `task_run_id` 管理，不占用模型轮次。

- 一个绑定会话同时最多一个普通轮次，后续消息排队；停止和取消命令走独立优先入口。
- `waiting_confirmation` 不占用活跃 worker 或阻塞后续轮次；以数据库提案状态承载等待，后续文字/按钮创建新的可处理事件。
- 用户对待确认方案补充条件时修改该方案并使旧按钮失效；已经执行的方案不能被追溯修改。在接收有效绑定的普通文本时，先在 inbox 事务内提升会话 intent_epoch 并封锁旧提案确认，再排队解析；不能在旧按钮已确认后才处理先收到的补充条件。确认 CAS 同时检查 intent_epoch 和待处理普通文本。若确定新文字不改变方案，才可在原期限内显式恢复，禁止自动续期。
- 正在处理时收到新消息，立即显示已排队；不把用户尚未处理的新条件当成旧方案已确认。
- 运行状态、结果计数和成功/失败卡片由服务端从实际 TaskRun/Operation 记录生成；模型仅补充解释，不能凭最终文字把 queued、partial 或 unknown 变成完成。没有业务结果时回复“尚未执行/尚未确认”，不编造任务 ID 或匹配数量。
- 模型请求和工具输出之间保存完整协议状态。重启后只允许恢复没有歧义的只读步骤、已接受提案和业务幂等步骤；不自动重新运行一段中断的自由生成写入对话。
- 在模型返回到业务写入之间再次检查 turn 的取消状态。旧 goroutine 即便在超时后返回，也不能继续写入。

### 8.2 上下文与数据保留

- 首版保留最近有限轮次及当前草稿/任务 ID。建议最多 20 轮、编码后 64 KiB；配置更大模型也不无限堆积。
- 工具调用与对应结果必须成对保留；清理上下文按完整轮次，不能生成孤立 `role=tool` 消息。
- 超限时提示开启新会话，保留服务器端结构化方案；首版无需自动摘要，避免摘要把邮件内容变成授权。
- 对话正文、工具输出和回复载荷使用 Vault 加密，AAD 绑定记录 ID。普通审计只存事件、主体、对象 ID、状态码和关联 ID。
- 建议聊天/交互载荷默认保留 7 天，业务幂等和最小审计默认 60 天；这些是新数据的保留建议，不改变现有邮件元数据和任务记录的保留策略。
- 清理只处理终态、过期且没有活动提案/任务/投递依赖的记录。未处理 inbox、未完成步骤和待核验关联不能按年龄直接删除。
- 幂等载荷清理后保留必要去重墓碑和处理水位，或通过已过期事件门禁保证旧事件不能重新建业务对象。
- `/new` 清空本会话可用上下文并使待确认提案失效；不删除业务任务或审计，不宣称磁盘安全擦除。

### 8.3 运行与停用

- 建议首版全局只同时执行一个模型轮次，其余排队；邮箱任务仍遵守现有执行并发限制。
- 队列有界，建议最多 100 个待处理轮次；满载时返回忙并给出状态，不丢弃已经确认接收的工作。
- 禁用 Agent 会取消模型请求和未开始的 Agent 修改、失效提案；既有独立固定任务继续按原授权运行，UI 清楚说明其区别。
- `/stop` 原子取消当前 Agent 轮次、本会话已排队普通轮次及尚未开始的提案步骤，持久化 stop epoch/取消标记；恢复器先检查该标记，再恢复 accepted/applying 步骤，重启不能复活已停止工作。`/cancel <run_id>` 请求停止指定任务剩余项；二者不能混称回滚。
- 退出时先停止接收、取消请求、保存处理状态并等待 worker；与 Compose 15 秒停止窗口协调。长轮询 context 必须可取消，不能为等待网络阻塞退出。
- 模型或 TG 不可用时不影响现有邮件同步、Web、MCP 和固定任务；Agent 状态与应用基础健康状态分开报告。

## 9. Telegram 交互实现

### 9.1 凭据与现有通知共存

- 首版复用现有通知设置中的 Bot Token，保留一个凭据来源；交互开关与通知开关独立。
- 现有通知配置、Chat ID 和通知策略不能因启用交互被改写。通知发送仍去既有通知 chat，Agent 回复只去经过绑定的私聊。
- transport 通过窄凭据读取接口取得已校验快照，解密只在发送/轮询进程内；不提供返回 token 的管理 API。
- 用 `getMe` 确认稳定 bot ID。凭据代际、bot 身份、交互配置版本分开，普通通知策略修改不重置 inbox 游标。
- token 被清除/替换、bot 改变、绑定被撤销或管理员版本变化时停止旧消费者，使旧提案失效；首版保守要求重新绑定。相同 bot 的 token 轮换保留去重水位，换 bot 则使用独立命名空间。
- 凭据更新时不得让旧 HTTP 请求返回的结果写进新代际状态；提交前核对 generation。
- 每次交互开关从关闭变为开启，都创建新的接收 epoch 和起始时间；同 bot 保留 offset 和去重水位，旧 epoch 未接受事件不执行，旧请求不能提交到新 epoch。关闭时取消未开始的交互工作并失效方案；重新开启不复活它们。

### 9.2 绑定流程

1. 管理员在 Web 开启交互、检测 token，选择 Agent grant，生成一次性绑定码。
2. 绑定码使用至少 128 bit 随机值、只存哈希、默认 5 分钟过期，绑定当前 admin/bot/config 代际；Web 只在创建时展示。
3. 用户私聊 Bot 发送 `/bind <code>`；服务验证 `chat.type=private`、真实 `from.id` 和 chat ID，原子消费绑定码。
4. 记录 Telegram 数字用户 ID、私聊 Chat ID、bot ID 和 grant。首版仅一个活动管理绑定，允许 Web 撤销后重新绑定。
5. TG 回复授权范围和可用命令；绑定不自动打开邮箱写入、扩大自动化策略或启用任何任务。

未绑定消息不进入模型、不透露邮箱信息；对绑定猜测做用户维度与全局节流。username、显示名称、转发原文、消息里的用户 ID 都不能代替真实 sender。绑定码不留在聊天上下文和普通日志。

Telegram user/chat/update 标识使用可容纳其范围的整数类型，Go 侧至少 int64；不得通过浮点数解析后比较身份，也不能截断为 32 bit。

仅接收绑定私聊中的原创文本和按钮回调；群聊、频道、匿名 sender、转发消息、编辑消息、附件和 inline mode 首版拒绝或忽略。回调必须有可验证的原消息/chat，不接受无消息的 inline callback。

### 9.3 长轮询与持久 inbox

- 首版仅支持 `getUpdates` 长轮询，建议 Telegram timeout 25 秒、HTTP 超时 35 秒，使用可取消 context。
- 启动时查 `getWebhookInfo`。存在 webhook 或 409 消费冲突时报告配置冲突并停止重试风暴，保留既有 webhook；不得静默 `deleteWebhook` 或 `drop_pending_updates`。
- `allowed_updates` 明确仅 message 和 callback_query；仍正确处理不支持事件，避免毒消息卡住游标。
- 数据库保存每个 bot 的 `next_offset`、poller lease、lease generation；单进程不得启动重复 goroutine。共享同一状态库的消费者使用租约与 fencing；不同库同时使用同一 token 的情形只能检测冲突并停用，不能声称可全局去重。
- 一批返回更新先验证大小与结构，事务内落库可处理事件或被拒事件的最小墓碑，并推进该批 `next_offset=max(update_id)+1`；事务失败不推进。
- 下一次 `getUpdates(offset=next_offset)` 才对 Telegram 确认。业务处理与拉取分离，不能等模型返回再推进 offset。
- 不假定 update_id 连续；长期无更新后 ID 可随机变化。按 Telegram 实际返回顺序和本批水位处理，不等待不存在的编号。
- 未授权事件只存最小元数据/拒绝结果，不长期保存原文；消息正文在落库前受大小限制并加密。
- 首次启用记录接收起始时间，旧 backlog 不触发管理动作；普通文本命令超过 10 分钟只提示重发。已持久化并接受的业务步骤按自己的恢复规则处理。
- callback_query 没有独立消息发送时间，不能拿卡片原消息的 date 当点击时间；用提案期限、绑定和当前服务时间判断。
- 明确说明 Telegram 服务端最多保留 24 小时更新，离线超过该时间无法保证补齐所有消息。

### 9.4 命令、按钮与发送

确定性命令至少支持 `/help`、`/status`、`/new`、`/stop`、`/cancel <run_id>`、`/bind <code>`。查询基础服务状态、停止和取消不得依赖模型可用。

- 接收后尽快返回简短回执；模型处理通过后台轮次继续。`answerCallbackQuery` 在模型处理前响应，防止按钮一直转圈。
- 可用按钮包括试运行、保存/启用当前方案、暂停、查看进度、取消。仅显示当前身份可用的动作。
- 默认使用纯文本，模型输出不直接解释为 Telegram HTML/Markdown；后续格式化必须正确转义。
- 文本按 Unicode 边界拆分，建议每片最多 3500 UTF-16 code units，避免超过 4096 限制或拆坏代理对；长内容摘要加分页。
- 新交互 outbox 保存回复语义 key、片号、chat、目标 message ID、投递状态和重试时间；每片唯一。
- 进度消息合并更新，只在状态改变时编辑；最终结果与原通知按事件语义避免重复轰炸，同时保留原任务通知策略。
- 429 遵循 retry_after，网络错误有界重试；401/403 显示 token/绑定故障。原始 API 错误里可能含 token URL，不得直接记录。
- Telegram sendMessage 发出后超时可能已经送达。标记投递结果未知；允许少量重复提示，但不能据此重试业务写入。已知 message ID 优先编辑。
- 交互发送与原通知共享每 bot/chat 的速率协调，避免相互触发限流；两种开关和队列状态仍独立。

下表为逻辑模型，允许合并强相关表，但实施时必须保留唯一约束、版本、状态和恢复语义。DDL、索引和外键需在代码中给出，并写迁移测试。

| `telegram_inbox` | bot_id/update_id 唯一、binding、类型、加密载荷、接收/事件时间、状态、失败码 |
| `agent_conversations` / `agent_turns` | binding、上下文/intent/stop epoch、序号、输入事件唯一、状态、deadline、lease/fencing |
| `agent_messages` | turn、role、tool_call_id、加密载荷、binding/grant/admin/config 版本；按完整轮次读取 |
| `agent_tool_calls` / `agent_mutations` | turn/ordinal 唯一、服务端 action_id/mutation_id、参数摘要、目标/版本、状态和结果；业务 mutation_id 唯一 |
| `agent_proposals` / `agent_proposal_steps` | token_hash 唯一、范围/版本摘要、期限、CAS 状态、步骤 mutation_id 和实际结果 |
| `agent_run_links` | conversation/turn/proposal 与现有 task_run_id 关联；不复制运行事实来源 |
| `telegram_reply_outbox` | semantic_key/part 唯一、bot/chat、binding/grant/admin/generation、加密载荷、message_id、状态/attempt/next_attempt/lease |

要求：

- 从最新 schema 递增；若实施基线仍为 schema 9，通常进入 schema 10。SchemaVersion、迁移 PRAGMA 和升级文档一致，禁止修改旧迁移假装新 schema 已存在。
- 迁移事务失败全部回滚；已存在实例首次迁移后新功能关闭，原任务、通知策略、文件夹映射、邮件、密钥和待核验状态保持完整。
- 为 inbox 待处理、outbox 到期、proposal 过期、turn queued 与 lease 回收建立索引。
- 不在 DB 事务内调用 `getMe`、getUpdates、模型、发送消息或 IMAP；关闭 rows 后再发网络请求。
- 加密载荷不得复制到普通 payload 列、诊断文件或 error_detail。对敏感记录删库不宣称安全擦除。
- 表级外键删除行为不得级联删除仍需用于远端核验的既有 operation/run；账号移除和解绑后保留最小审计并屏蔽内容。
- 对新建库、schema 9 升级、重复启动、迁移失败、错误密钥、新旧二进制拒绝规则分别测试。
- 旧二进制通常拒绝新 schema。回滚采用升级前一致性快照与配套主密钥，不手工改 PRAGMA 或直接让旧镜像打开新库。

## 11. 管理 API 与界面契约

以下路径为建议命名。Claude 可按现有路由风格调整，但必须在交付中列出最终契约；全部接入现有管理员认证、CSRF、Origin、大小限制和响应头。

| 方法/路径 | 功能 |
| --- | --- |
| `GET/PUT /api/agent/provider` | 读取脱敏配置；期望 version 更新配置和密钥 |
| `POST /api/agent/provider/check` | chat 或 tool_loop 检测；只执行无副作用测试工具 |
| `GET/PUT /api/agent/grant` | 授权范围、动作、有效期，期望 version 更新 |
| `POST /api/agent/grant/revoke` | 撤销 grant 并失效待确认方案 |
| `GET/PUT /api/telegram/interaction` | 交互开关、配置版本、bot 与接收状态 |
| `POST /api/telegram/bind-code` | 创建一次性绑定码，不可通过 GET 重读 |
| `POST /api/telegram/unbind` | 撤销绑定、取消未开始工作和待确认卡片 |
| `GET /api/agent/conversations` | 分页会话摘要，不返回密钥或默认展开原文 |
| `GET /api/agent/turns/{id}` | 授权管理员查看脱敏状态、工具调用和业务关联 |
| `POST /api/agent/turns/{id}/stop` | 停止当前轮次，语义与 TG `/stop` 一致 |

具体规则：

- GET 不产生模型调用或状态修改；异步测试可返回 202 与检测 ID，并提供短轮询状态。
- 配置写入使用乐观锁。过期 version 返回冲突，界面提示重新加载，不自动覆盖。
- 字段沿用 snake_case，未知字段、重复/尾随 JSON、非法枚举和过大输入被拒绝。
- 输出固定错误码，如 `provider_auth_failed`、`tool_call_unsupported`、`provider_rate_limited`、`binding_required`、`grant_expired`、`proposal_expired`、`state_conflict`、`delivery_unknown`；配中文说明，不返回供应商原始正文。
- UI 清楚区分 Provider 配置完成、聊天可用、工具闭环可用、TG 凭据有效、轮询在线、已绑定、拥有执行授权。
- 页面必须能看到观察/执行模式、有效每批数量、保护开关、时区和未来 5 次日程。
- 默认“Agent 与 Telegram”设置页即可，不新建完整聊天产品。保持无 Node 构建依赖、静态脚本与现有 CSP。
- Provider 测试/断网失败不把 `/readyz` 改为不健康，防止模型供应商故障触发容器重启风暴。

| --- | --- | --- |

| P3 工具与提案 | 首版共享工具、Schema、只读草稿预览、差异、CAS、业务 mutation 幂等 | 禁用规则预览无临时启用；创建/更新崩溃窗口、重复确认、依赖规则、部分完成测试 |

## 13. 自动化测试与故障矩阵

使用 `httptest`/假 Provider、假 Telegram、现有 Remote 测试设施和临时 SQLite。默认测试离线、不调用真实模型、不花费 API 额度、不碰生产邮件。每项高风险机制应有能证明失败路径的测试，不能只断言函数返回 nil。

| 编号 | 场景 | 验收断言 |
| --- | --- | --- |
| T01 | 普通聊天成功但工具不支持 | 显示两种能力差异，写操作 Agent 不能启用 |
| T02 | 多工具调用、Unicode、转义、额外字段、截断参数 | call/result 正确关联；非法参数零业务写入 |
| T03 | Provider 401、429、5xx、超时、超大响应 | 固定错误码、有界重试、能停止；无凭据/正文泄露 |
| T04 | Base URL、重定向、IPv6、DNS 重绑定、默认代理 | 不能把 API Key 发往未允许目的地址 |
| T05 | 修改模型/地址/密钥后复用旧检测 | 检测失效，旧 in-flight 结果不能覆盖新配置 |
| T06 | 自称管理员、伪造 owner/grant、邮件主题含工具指令 | 不改变身份/权限，不自动确认或执行 |
| T07 | 生成建议后撤销、到期、缩小范围或修改管理员凭据 | 下一个写入被拒，旧按钮失效；历史上下文不再进入模型、旧回复抑制，原核验不重放 MOVE |
| T08 | 跨账号/文件夹任务与历史运行、普通 MCP token 跨 owner | Agent 按专用 grant 收窄；MCP 原限制保持 |
| T09 | 禁用规则与待建任务预览、创建任务、启用规则、绑定高优先级闭包 | 草稿预览零启用/零远端写入；实际新任务暂停观察；影响任务越权则拒绝；不绕过高优先级保护 |
| T10 | patch 未包含 max_batch/未读/星标/Since | 原值保留、有效保护取业务策略结果，无每日限额 |
| T11 | 预览一页/稀疏匹配/未知字段/无候选 | 区分本次扫描与全量；0 候选不声称远端写入验证成功 |
| T12 | 确认前规则/策略/映射/任务/依赖集合发生变化，或补充条件已接收尚排队 | 旧提案冲突或封锁；不能用“确认”覆盖新状态或抢在先到条件前执行 |
| T13 | 双击按钮、重复 update、并发相同 mutation | 同一资源、同一版本修改、同一 task_run；没有重复创建 |
| T14 | 业务事务前、提交后结果返回前、outbox 发送前崩溃；模型重试返回不同 call ID/ordinal | 恢复沿用原 action_id 与既有结果；不盲目再建规则/任务/运行 |
| T15 | 多步骤只完成前半部分后重启或遇到冲突 | 明确 partial、保留已完成资源；不自动覆盖或回滚 |
| T16 | inbox 写入失败、轮询响应后崩溃、重复批次 | offset 只在整批持久化后推进；业务最终可处理 |
| T17 | 更新编号有间隔、长期闲置、超旧 backlog、毒事件 | 不等不存在 ID；旧命令不触发写入；能继续处理新事件 |
| T18 | webhook 存在、重复 poller、不同 DB 的 409 | 不静默删 webhook、不重试风暴，明确停用/冲突 |
| T19 | 换 token、换 bot、解绑、再绑定、交互关闭后重开期间旧请求返回 | 代际围栏有效；不把旧消息发给新绑定，不重复消费，停用期间旧命令不补执行 |
| T20 | 群聊、转发、编辑、伪造 sender、过期/重复绑定码 | 零模型调用或业务写入；有效绑定码只能消费一次 |
| T21 | 伪造/过期/旧会话 callback，重复点击 | 真实 sender/chat/提案校验，CAS 生效，回调及时应答 |
| T22 | 中文/emoji 长回复、特殊标记、429、发送后超时 | 分片合法、纯文本、消息可重试而业务不重放 |
| T23 | 模型挂起时 /status、/stop、/cancel，停止后立即重启 | 不依赖模型，及时接受；当前/queued/未开始提案不复活，旧响应返回后不能再写 |

| T25 | 模型工具循环、上下文/输出/队列超限 | 有界退出、协议消息不残缺、不无期限耗费 API |

## 14. 端到端验收脚本

先用假服务覆盖所有流程，再用专用测试 Bot、配置好的兼容 API 和专用测试邮件验证。真实测试资源须与日常邮箱数据明确区分；预览有历史真实邮件时不能为了验收执行批量清理。

### A. 从空配置开始

1. 升级后确认 Agent/TG 交互关闭，原同步、任务、通知正常。
2. Web 填入 Provider，聊天与工具闭环分别检测；错误 key 可见错误且无泄露。
3. 设置只覆盖测试账号和目录的 grant，生成绑定码；另一个 Telegram 用户/群聊不能操作。
4. 绑定后读取可见账号、目录和任务；范围外数据不可见。

### B. 创建并启用固定规则

用户示例：“把测试发件人超过 30 天的邮件移到回收站，保留未读和星标，每周五 20 点执行。”

- 若未指定邮箱或发送者实际地址，Bot 明确询问缺失条件，不猜测影响整个邮箱。
- 展示 Asia/Shanghai、准确条件、原邮箱回收站映射、保护、有效批次和未来 5 次日程。
- 新规则禁用、待建任务保留在方案中；只读草稿预览无临时启用或远端写入，展示分页统计与样例。已有启用规则的实际新任务则必须暂停观察。
- 补充“只处理收件箱”后旧卡片失效。
- 确认当前方案后，按实际版本逐步启用，最终状态可从 Web 查询一致。
- 若受限于未授权 trash/internal/execute，草稿可保存但不会自动扩权；Web 授权后重新预览和确认。

### C. 执行、查询和停止

- “立即执行刚才任务”创建一个运行，TG/Web 结果指向同一 task_run_id。
- 重投同一 update 和重复点击不创建第二个运行；另一条明确执行指令可形成新运行，仍受账号活跃运行限制。
- `/status` 能在模型不可用时工作；`/cancel <run_id>` 能停止授权范围内的固定规则运行剩余项。
- 结果分别列已完成、失败、保护跳过、未知待核验和未完成数，不把未知算成成功。
- 专用测试邮件在原邮箱确实移动，未读/星标保护邮件留在原位置；不调用永久删除或全局 EXPUNGE。
- 内置定时运行由服务自身触发，TG 可通过专用授权查询和停止；普通 MCP token 仍不能跨 owner 操作。

### D. 故障恢复

- 等待确认时重启，未过期方案可正确展示；版本变化后拒绝旧确认。
- 已确认且业务提交完成、TG 回复前重启，恢复后返回同一规则/任务/运行。
- 模型超时、TG 429、发送结果未知不影响已有邮箱任务和同步。
- token 轮换、解绑、grant 撤销后旧消息与旧按钮失效。
- 生产升级与快照回退各演练一次；回退恢复后的旧绑定/提案不得自动恢复写权限。

- 提交前检查暂存内容，排除 `.planning/`、AGENTS.md 等未跟踪私有工作文件（除非用户明确要求纳入）、凭据、邮件数据、私有部署配置、截图原文和临时诊断程序。
- 本文为无凭据设计文档，可纳入后续实施提交；本地审计证据放 `.planning/` 或其他明确排除目录，不跟随提交。

### 15.2 发布与部署

1. 提交并推送远端仓库；记录 commit SHA 和远端验证状态。
2. 发布对应 Git 标签和新版本镜像，同时发布版本标签与 `latest`，包含 linux/amd64、linux/arm64。
3. 从 registry 重新读取 manifest/index 与平台摘要，核对两个标签和实际构建产物；不能只用本地 buildx 输出代替核对。
4. Oracle1 `/opt/1panel/docker/compose/mail_auto` 先记录旧镜像、实际版本、健康与重启数，创建一致性数据库快照并单独保护主密钥/部署配置。

7. 记录至少一次容器重启前后行为、两个完整全文件夹自动校对周期、一次实际固定规则任务和测试 TG 对话。网络慢时等待实际周期结束，不能用固定短等待代替完整证据。

### 15.3 回退与成功后清理
