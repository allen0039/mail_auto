# 0.8.7 验收记录：LE-01、LE-02 补修

范围：只修复 0.8.6 独立审计的 LE-01、LE-02（P2，均为任务编辑器显示）。

- 只改 `internal/admin/web/tasks.js` 中摘要与写入说明的显示，以及对应回归与版本文件。
- 任务字段、保存载荷、继承方式、后端授权语义与接口均不变；数据库仍为 schema 13，无迁移。
- 本文件不声明验收通过，交由 Codex 独立复验。

证据标记：**[模拟]** 隔离临时实例 + 假数据接口；**[本地后端]** Go 测试中的真实处理与 SQLite；**[生产只读]** Oracle1 只读查询；**[真实写入]** 原邮箱实际写入（本版没有）。

## 1. 修复方式

### LE-01：摘要显示整理授权仍施加的约束

`renderEditorSummary()` 按后端 `taskRunPolicy` 的合并规则（每批取较小值、历史起点取较晚值、保护取任一要求）计算显示值，读取页面已载入的整理授权，不新增接口，也不改任何字段。

| 情况 | 摘要显示 |
| --- | --- |
| 授权保护未读和星标，任务未额外保护 | `保护未读和星标（自定义；任务未额外保护，整理授权仍要求保护）` |
| 授权也不保护 | `不保护未读和星标（自定义）`（如实） |
| 授权历史起点晚于任务起点 | `只处理 <授权起点> 起收到的邮件（自定义；任务设为 <任务起点>，整理授权起点更晚）` |
| 任务未设起点，授权有起点 | `历史范围跟随整理授权（<授权起点> 起）` |
| 授权每批上限低于任务设置 | `每轮最多 <授权上限> 封（自定义；任务设为 <任务值>，受整理授权上限 <授权上限> 限制）`；输入框仍为任务值 |

### LE-02：创建成功后继续编辑，写入说明跟随当前表单

保存成功但保存期间又有编辑（`after === "edited"`）时：

- 采用已创建的 ID、版本后立即调用 `renderEditorSummary()`。写入说明、`task-mode-write` 样式和摘要按当前表单重新显示。
- 不重开、不重置表单，不改模式选择。
- 较新草稿、未保存标记、ID 与版本保留，下次保存为 PUT。

## 2. 独立复现步骤

1. 安装检查依赖：`npm i puppeteer-core`。
2. 运行：`PUPPETEER=<路径>/node_modules/puppeteer-core scripts/ui-check/run.sh scripts/ui-check/task-editor-ui-check.js`。
   - 检查使用隔离临时实例、一次性凭据和假接口，不连接邮箱，不调用模型。
3. LE-01（检查第 7 段）：
   1. 假接口的整理授权设为：保护未读与星标、起点 2026-11-01。
   2. 打开“宽松任务”（不保护、起点 2026-10-01、每批 12）。摘要应为上表第 1、3 行，并原样 PUT 保存。
   3. 把授权每批上限改为 10 再打开，摘要应为上表第 5 行，输入框仍为 12。
4. LE-02（检查第 8 段）：
   1. 新建任务，选“真实执行”（或“只观察”）后提交，延迟响应。
   2. 保存期间修改名称（只观察时还修改通知），然后放行创建响应。
   3. 写入说明应为“真实执行：运行时会移动或修改原邮箱…”（或“只观察：运行时只记录建议…”），不应再出现“新任务保存为…”。
   4. 再次保存应为 `PUT /api/tasks/t-new`，version 1，带较新名称与当前模式，POST 只有 1 次。
5. 审计探针：`run.sh .planning/audit-0.8.6-20261115/task-edge-check.js`。
