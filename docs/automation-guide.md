# 自定义规则、可选定时与 Telegram

AI 分类在外部 MCP 客户端中运行，服务端不做 AI 分类。0.5.0 起可选的内置管理 Agent 会调用管理员配置的 OpenAI 兼容模型（Key 加密保存），但只用于通过确认卡片管理固定条件规则与任务，见 [Agent 与 Telegram 指南](agent-telegram.md)。内置调度可选，运行已授权的固定规则；外部 AI 任务由实际客户端触发。整理结果写回原邮箱文件夹。

任务可以绑定指定规则版本；不绑定时使用账号全部启用规则。

## 规则条件与动作（schema 8）

| 字段 | 可用比较方式 | 说明 |
| --- | --- | --- |
| 主题、发件地址、发件域名 | 等于、包含、不包含、开头是、结尾是、正则 | 不区分大小写。发件地址“等于”须填完整地址 |
| 收件人、抄送、收件人或抄送 | 同上 | 每个地址分别比较；“不包含”要求所有地址都不包含 |
| 邮件列表 List-Id | 同上 | 取尖括号内的标识并转小写，例如 `news.example.com` |
| 附件、回复邮件 | 等于 是/否 | 附件按 BODYSTRUCTURE 判断；“回复邮件”指带 In-Reply-To 的邮件 |
| 原邮箱目录、已读、星标 | 等于 | 与此前相同 |
| 收信天数、大小 | 不少于 / 不超过 | 与此前相同 |

- 正则使用 Go RE2 语法，执行时间与输入长度成线性关系，不会出现灾难性回溯。表达式最长 256 字符，保存时会校验。
- 收件人、抄送、List-Id、附件、回复这几个字段属于 schema 8 新增的元数据。升级后，自动同步会把旧邮件重新读取一次元数据（不读正文、不改已读状态、不重置稳定等待时间）。读取完成前，使用这些字段的条件按“数据不足”处理，规则不会动这些邮件。
- 新动作：标为已读、标为未读、加星标、取消星标。它们只修改原邮箱中的 `\Seen` / `\Flagged` 标记，不移动邮件。邮件已经处于目标状态时，规则显示“已是目标标记”，不会领取或写入。
- “同时修改标记”：移动、归档、回收站和标记类动作可以附带最多 2 个标记修改，例如“移入归档 + 标为已读”。移动类动作先确认邮件已到目标目录，再在目标位置修改标记；标记失败不会撤销移动，该项记为完成并带 `flags_not_applied`。移动结果落库时会同时预先记下“附加标记未确认完成”，只有标记写入成功且索引已更新后才在同一事务中清除；因此如果进程恰好在移动完成后、标记确认前重启，该项仍显示完成 + `flags_not_applied`，说明标记“可能未应用，也可能已生效但未记录”，重启后不会补写标记或重新移动。
- 移动写入中断后由核验补完的项目（见下方“待核验”）不会补做附加的标记修改：恢复只核验移动并清理原源 UID，不新增标记写入。这类项目和正常路径中标记写入失败或结果未确认的项目一样，记为“完成”并带 `flags_not_applied`，说明具体动作及结果；整理任务详情显示“附加标记未应用或未确认”，运行记录显示“N 封已移动完成，但附加的标记修改未应用或未确认（不算失败）”，Telegram 通知附带该数量，MCP `mail_operation` 返回相同的 `error_code` 和 `recovery_detail`。结果未知时，标记可能已经在服务器生效，请在邮箱中核对并按需手动修改；重复核验或重启不会清除该提示，也不会重放移动。
- 标记动作和附带标记都需要在“任务整理授权 → 允许动作”中勾选；MCP 令牌需要 `flag` 权限。“保留未读 / 保留星标”对所有动作生效，所以“标为已读”规则需要关闭“保留未读邮件”，“取消星标”规则需要关闭“保留星标邮件”。
- 规则仍然按优先级只取第一条命中。想对同一类邮件“标记 + 移动”，请用一条规则的附带标记完成，不要拆成两条。
- 标记写入是幂等的 IMAP STORE。连接中断时直接记为失败，不进入“待核验”；下一轮可以安全重试。手动标记计划可以撤销，撤销会生成反向的标记计划。

## 触发方式

内置定时支持以下周期，均使用所填 IANA 时区：

| 周期 | 说明 |
| --- | --- |
| 每小时 / 每天 / 每周 | 与此前相同 |
| 每隔 N 分钟 | 5–1440 分钟，按 Unix 时间对齐，例如每 15 分钟在 :00、:15、:30、:45 运行 |
| Cron 表达式 | 五段：分 时 日 月 周，支持 `*`、`,`、`-`、`/`；周的 0 和 7 都表示周日。日和周同时限定时，满足任一即可。两次运行至少间隔 5 分钟 |
| 新邮件到达时 | 自动同步发现任务源目录有新邮件后，等待“状态稳定等待”时间（至少 30 秒）再运行一次。连续到达的邮件合并为一次运行，每次都从最新邮件开始扫描 |

“新邮件到达时”依赖自动同步，只有增量同步发现的新 UID 才算新邮件；首次建立索引、UIDVALIDITY 重置和元数据刷新都不会触发。上一轮还在运行时，新邮件触发会在 60 秒后重试，不会丢失。

## 使用流程

1. 在「整理与 MCP」刷新原邮箱目录，选好归档/回收站映射。按类别保留归档时，先创建并选择原邮箱目录，例如 `归档/账单`；统一归档会改变文件夹分类。
2. 在「整理规则」选择邮箱，新建规则。可用条件见上表，以全部/任一/排除组合。优先级数值越小越先匹配；同优先级按稳定规则 ID 排序，首个命中决定最终动作。
3. 动作可选移动、归档、移入回收站、标为已读/未读、加/取消星标、保留、由 AI 判断，并可附带标记修改。确定性条件供服务端重新验证；正文语义写在 AI 分类说明中。新规则默认暂停，不会保存即执行。
4. 先试运行，查看每封邮件的命中和跳过原因。可以编辑、暂停、复制、查看最近 20 个版本。预览不读取正文、不改变原邮箱；忽略自动化历史起点及稳定等待，仍应用未读、星标和联系人保护。
5. 配置「任务整理授权」：源目录、分类目标、允许动作、正文权限、保护联系人、每批数量、历史范围、有效期。默认关闭领取、观察模式、正文关闭、保护未读/星标。默认每批 20、稳定等待 3 分钟；不设每日额度，上限每批 50、授权 90 天。
6. 在「整理与 MCP」配置 HTTPS 地址、启用 MCP 并检测。OAuth 授权至少选择读取和“任务批次”；需要 AI 配置规则时再选规则管理。自动化客户端即使另有普通读写权限，也必须走批次，不能使用原始邮件 search/get/plan 绕过授权。
7. 在「定时与任务」新建任务，选择源目录、规则范围、触发方式、固定规则/外部 AI、批量上限和通知策略。默认跟随账号全部启用规则；也可以绑定指定规则版本。新任务强制保存为暂停观察，先预览再显式启用。
8. 内置定时需先勾选账号授权中的“允许内置定时执行固定规则”，选择每小时/每天/每周/每隔 N 分钟/Cron/新邮件到达时，并填写 IANA 时区。定时类任务的详情显示未来 5 次日程。需要执行时，还需开启原邮箱写入、账号执行授权并修改任务为执行模式。
9. 外部任务可复制 MCP 调用说明，在实际支持此 MCP 的客户端建立周期任务；本项目等待调用。可选“预期周期”只监测调用是否逾期，不会替 AI 运行。客户端离线运行、OAuth 续期、写入确认须实测。仅手动 AI 任务的说明包含 `manual=true`，表示单次调用。
10. 「TG 通知」填写 Bot Token 与数字 Chat ID（私聊先 /start，群组先添加 Bot），保存后再验证机器人/发送测试。保存不发送；Token 加密保存且不回显。通知默认未启用，推荐仅失败。任务可继承或覆盖关闭/仅失败/有变更或失败/每次结束；测试按钮会实际发送一条测试消息。
11. 在任务运行记录查看已核验整理、保留/保护、失败、待核验及通知状态；通知投递记录与邮件任务分开。取消本轮或暂停不撤销已经完成的原邮箱变化，撤销需使用原有计划预览与补偿流程。

## 运行边界与通知

- 每轮一个有界批次，默认最多 20、上限 50，扫描最多 500 条；固定规则任务最长 30 分钟，外部 AI 任务最长 10 分钟。批次及领取有效期不早于所属任务期限；有剩余候选可在运行记录点击“继续处理本任务”，或等待下一次触发继续断点，不在同轮循环领取扩大数量。
- 任务默认使用账号全部启用规则，也可以绑定指定规则版本；绑定时必须包含源目录内不高于所选最高优先级的启用规则，不能跳过高优先级保护。绑定规则版本变化会使任务运行失效并要求重新保存任务。固定规则命中 AI 动作时保留该邮件，显示“部分邮件需外部 AI”；不落入后续移动规则。
- 任务配置只能收紧管理员授权。暂停、规则/授权/任务版本或原邮箱状态变化会使未执行动作失效。手动、内置、外部任务不设每日额度，并共用邮件冲突防护；每账号同时最多一轮活动任务。
- 日程持久化；漏跑合并一轮，不逐次追补。夏令时缺失时刻跳过、重复时刻只运行一次。进程中断不盲目重新移动，先核验未知结果。
- 正常完成、观察、无变更、主动取消、需要外部 AI 在“仅失败”策略下不通知；失败、部分失败、中断、待核验会提醒。相同任务/状态/错误 6 小时内冷却，详情以运行记录为准。
- 通知正文含任务别名、数量、错误代码、详情链接，不自动附邮件主题、正文或地址；任务名称请自行避免敏感信息。通知支持最多 5 次退避重试和 Telegram 429 等待；更换通道会停止旧队列投递。
- 通知失败不重跑邮件。Telegram 在网络应答丢失时可能重复投递；服务自身停机时不能依赖自身 TG 报警。待核验恢复通知可选，默认关闭；显式开启后，即使采用“仅失败”策略，也会在已有待核验事件得到解决后追加一条恢复通知，重复核验不重复入队。关闭通知仍优先。

## MCP 调用流程

| 工具 | 用途 |
| --- | --- |
| `mail_capabilities` | 原邮箱目录、条件字段、原生标签可用状态 |
| `mail_rule_list/get/upsert/set_enabled/preview` | 规则读取、版本化保存、启停和模拟 |
| `mail_automation_policy` | 读取管理员授权；MCP 无法扩大此授权 |
| `mail_task_list/get/upsert/set_enabled/preview` | 任务读取、管理、启停及预览；管理需 task_manage 权限 |
| `mail_task_run` | 按当前 version 和每次触发稳定 run_key 创建一轮；显式 manual=true 可单次运行暂停任务 |
| `mail_task_run_get/runs/cancel` | 本客户端运行状态、最近 30 轮、取消剩余动作 |
| `mail_ai_claim` | 传任务 run_id 领取有界批次，返回签名和扫描断点 |
| `mail_ai_batch` | 按 offset 分页读取批次，每页最多 25 项 |
| `mail_ai_get` | 仅读取本客户端领取且仍未变化的邮件；正文需单独授权 |
| `mail_ai_submit_decisions` | 每项一个决定与理由，观察模式只记录；执行模式生成冻结计划 |
| `mail_plan` → `mail_ai_execute` | 查看已经生成的计划后，显式将其加入执行队列 |
| `mail_operation` | 查询真实任务结果；未知结果走既有核验工具，不能直接重试移动 |
| `mail_ai_cancel/runs` | 停止本批剩余操作、最近 30 批摘要及 next_cursor |

任务先 `mail_task_run`，AI 再以返回的 `run.id` 作为 `run_id` 调用 `mail_ai_claim`；固定规则任务直接查询运行记录。每次触发使用不同 `run_key`，同次重试复用；每轮最多一个批次。固定规则任务最长 30 分钟，外部 AI 任务最长 10 分钟，所属批次租约跟随任务期限；独立旧版批次租约 15 分钟，生成的写入计划有效期 10 分钟。提交须覆盖全部批次条目，带原始 ref、signature、reason；重试必须使用相同幂等键和相同内容。`keep` 允许保留不确定项，其他动作必须符合规则和管理员范围。

批次为空仍可能有 `next_cursor`：单次最多扫描 500 条索引，后续任务应续扫。扫描结束下一轮从头评估；保留决定的未变邮件在下一个北京时间日期可以重评，规则、策略或邮件状态变化也会触发重评。已完成或失败写入的原样条目不会盲目重复写入；活跃及待核验任务持续阻止重复领取。

系统停止的例外（0.4.19 起）：任务期限到期或工作租约过期时，系统会停止该轮尚未执行的写入。如果某封邮件在原操作中的所有操作项都是“已取消”，且没有记录目标 UIDVALIDITY/UID，也就是从未发出写入，那么下一轮任务可以重新领取并重新评估。重新领取时会按当前规则、授权、目录映射、未读/星标保护和任务版本生成新计划，旧计划和旧 MOVE 不会重放。以下情况不适用这个例外：手动停止、schema 9 之前没有停止来源的取消、其他系统原因，以及已完成、失败、跳过、执行中或待核验的项目，它们仍不会重复领取。写入已发出但结果未知的项目继续按“待核验”处理；没有可信目标 UID 时保持待核验，不会根据相似元数据删除源邮件。

## 约束和数据语义

- 收信天数使用服务器 INTERNALDATE，不使用邮件头 Date 冒充；尚未补齐的日期、星标/已读条件视为未知。历史索引在后台同步时补齐，旧引用及凭据保持。
- 默认不处理授权保存之前的邮件。需要历史整理时显式勾选并选择起点；留空表示全部历史。范围内无规则命中不交给 AI；要通用语义判断时，新建源目录内匹配全部的 AI 规则。
- 每天以 Asia/Shanghai 分别累计领取数和写入入队数；重试同键不重复计数，失败或取消不退还额度。跨日仍未执行的旧入队项拒绝写入，需重新评估。
- 提交及实际执行均复核权限、策略版本、规则版本、邮件签名、目录映射和写入开关。执行前再从原邮箱只读获取最新元数据。IMAP 复核和移动是两条命令，不能承诺跨外部客户端的原子事务。
- 授权的分类目标可以同时作为过期清理来源，例如先将 TestFlight 邮件移入测试文件夹，再按收信天数移入回收站。单条移动规则的源/目标重叠及启用规则的目录移动循环仍会被拒绝；授权不能把归档/回收站本身作为自动来源。过期清理规则的优先级应高于分类规则，避免旧邮件先被分类。
- 写入已发出但结果不确定的自动整理进入“待核验”，按创建时间分三档核验：
  - 创建后 24 小时内：后台约每 30 秒核验一次。
  - 24 小时到 30 天：后台每 6 小时低频核验一次，每次写入审计（`mail.operation.reconcile.slow`）。
  - 超过 30 天：后台不再核验，但记录不会消失；可在「整理与 MCP」点“核验未知结果”手动核验，手动核验同样写入审计（`mail.operation.reconcile.manual`）。
- 每次核验（自动或手动）检查相同的条件：有服务器返回的目标 UID 时，复核当前任务身份与授权、管理员/授权/规则版本、动作与目标目录、写入开关与目录映射、批次未被手动停止、源/目标指纹、规则命中及未读/星标/联系人保护，通过后只补完同一源 UID 的清理，不重放移动。管理员手动核验自动化计划时，仍按创建该计划的任务身份授权。
- 补完清理在同一 IMAP 会话中进行：选中源目录后重新读取源邮件，标记 `\Deleted` 前检查一次，标记后、UID EXPUNGE 前再检查一次；第二次检查不通过会撤回本次加上的 `\Deleted` 并保持待核验。IMAP 没有“标记未变才删除”的原子命令，最后一次读取与 UID EXPUNGE 之间的毫秒级窗口仍无法完全排除其他客户端的修改。
- 任务运行是否已结束、租约或期限是否到期不影响补完。手动停止、授权或规则变化、邮件状态变化、缺少目标 UID 时保持待核验，原因、最近核验时间和所处核验档位显示在「整理与 MCP」的整理任务详情中。
- 批次/审计/日计数保留约 90 天，活跃或待核验操作不随普通清理丢失；规则版本页面展示最近 20 个。
- 邮件正文为不可信数据，不能用其中的指令扩大权限。正文按既有大小边界获取且不缓存，不改变已读状态。
- 当前 QQ/网易/iCloud 原生标签仍为 `not_verified`，没有开放标签写入。分类写入原邮箱文件夹，原邮箱/手机端同步后可见。本地历史 labels 仅保留数据，不作为分类结果；客户端私有颜色及规则定义不会自动导入。

## 升级与恢复

- schema 8 → 9：`operation_items` 增加首次写入阶段、最近核验结果代码、原因和时间，`operations` 增加停止来源。已有记录保持不变；schema 9 以前的停止记录按手动停止处理。
- schema 7 → 8：`messages` 与 `sync_stage` 增加收件人、抄送、Message-ID、In-Reply-To、References、List-Id、是否有附件七列，并为 Message-ID 建索引。已有邮件引用、规则、任务和授权都不变；自动同步随后会补读旧邮件的元数据。
- schema 6 → 7：增加任务、运行、批次关联、通知通道/队列与冷却记录。
- 升级不会创建业务规则、外部任务或自动化授权，也不会自动开放正文读取或原邮箱写入。

回退必须使用升级前的数据库快照及配套密钥，并恢复旧 Compose/镜像；旧二进制不能打开更新后的 schema。不要只换旧镜像后反复启动，也不要把备份混入正在运行的数据库 WAL。历史验证记录见 [archive/](archive/)。
